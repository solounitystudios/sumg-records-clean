## 1. Idempotency contract

```
KEY: idempotency_key — client-generated (UUID/ULID), created once when the
     user initiates an upload attempt (e.g. picks a file), persisted in the
     browser (sessionStorage or component state, not just in-memory) for the
     duration of that attempt.
GENERATED BY: client.
UNIQUENESS SCOPE: UNIQUE (uploaded_by, idempotency_key) on
     catalog_asset_versions — DB-enforced. Work/Recording scope deliberately
     does NOT participate: on the very first request the client doesn't yet
     know the resulting work_id/recording_id (they're created in the same
     request), so scoping uniqueness by them would create a chicken-egg
     problem. NULL idempotency_key values (worker-created lineage
     derivatives, which don't go through this path) never collide under
     Postgres's default UNIQUE semantics.
EXPIRATION: none enforced at the DB level. A non-terminal row
     (pending_upload/uploaded_unverified/verifying) with no progress for a
     long time is a RECONCILIATION finding (stale), not a hard expiry — see
     SUMG_MASTER_VAULT_SECURITY_CONTRACT.md §Reconciliation.
REUSABLE AFTER FAILURE: YES for non-terminal states — a retry with the same
     key against a still-pending_upload/uploaded_unverified/verifying row
     is a no-op "find the existing row, re-issue what's needed" operation,
     never a second row. NO for terminal states
     (verification_failed/cancelled) — the client must generate a FRESH key
     to represent a new, distinct upload intent; silently retrying a
     definitively-failed key would be confusing (unclear whether the user
     is retrying the exact same bad file or trying again). The server
     returns a conflict/guidance response, not a silent new row, if the
     same key is resubmitted against a terminal row.
CONFLICT RESPONSE: if a retry under an existing key reports different file
     metadata (size/mime/client_sha256) than the row already stores, that's
     a genuine client bug (key reuse across different files) — reject with
     a conflict, never silently accept the second file under the first
     key's identity.
DB-ENFORCED: the "no duplicate row" guarantee — yes, via the UNIQUE
     constraint, regardless of app-code bugs.
APPLICATION-ENFORCED: the terminal-state-conflict distinction and the
     file-metadata-mismatch check — Postgres's uniqueness alone can't know
     "is this a legitimate retry."
```

**Proven behavior, every scenario the brief listed:**

- **Browser retry / mobile reconnect:** client resubmits the same key (persisted through the reconnect) → server does an "insert; on unique_violation, select the existing row instead" pattern → same row, same signed-URL-issuing target, no duplicate.
- **User double-click / same request from two tabs / concurrent same key:** two near-simultaneous INSERTs race on the UNIQUE constraint; exactly one succeeds as a real insert, the other gets `unique_violation`, which the server catches and converts into "fetch and return the existing row" — idempotent by construction, not by luck.
- **Server timeout (response never reached the client):** client doesn't know if it succeeded, retries with the same key → same insert-or-select pattern returns the already-created row.
- **Different files accidentally using the same key:** detected by comparing the retry's declared file metadata against the existing row's stored metadata; mismatch → conflict, never a silent overwrite.

## 2. Manual Intake state machine — `upload_status`

Redesigned as the smallest machine that still handles real failures. Candidates explicitly considered and rejected, with reasons:

| Rejected candidate | Why |
|---|---|
| `draft` | Nothing is created before upload intent exists — there's no "fill in metadata, decide later" flow in V1 |
| `uploading` | The server never observes this moment (upload is direct client→Storage) — persisting it would need a needless mid-upload ping with no reader |
| `stale` | A reconciliation-report/derived condition (`updated_at` vs. a threshold), not a stored state — computing and persisting it would need a cron job for something a `WHERE` clause already answers |
| `quarantined` | Redundant with `catalog_review_flags.severity='critical'` — a second state overlapping the review-flag severity system is exactly the kind of duplicated concept this pass is trying to avoid |
| `upload_failed` (as a distinct state from staying `pending_upload`) | A failed signed-upload attempt just leaves the row in `pending_upload`, retryable with the same key; treating it as reconciliation-detected staleness (if truly abandoned) is simpler than a new terminal-ish state with its own transition rules |

**Final six states:** `pending_upload`, `uploaded_unverified`, `verifying`, `verified`, `verification_failed`, `cancelled`.

`review_status` (separate, unchanged: `pending_review`, `approved`, `held`, `archived`, `rejected`) tracks editorial judgment — orthogonal, not collapsed with the above. An item is normally `upload_status='verified'` AND `review_status='pending_review'` simultaneously; these are two independent dimensions, not a single combined enum.

### Transition matrix — `upload_status`

| State | Meaning | Allowed from | Allowed to | Actor | Auto/Human | Retryable | Terminal | Required fields |
|---|---|---|---|---|---|---|---|---|
| `pending_upload` | Row exists, signed URL issued, bytes not yet confirmed in Storage | (initial) | `uploaded_unverified`, `cancelled` | server (creation), client (confirm) | mixed | yes (re-issue signed URL) | no | `idempotency_key`, `uploaded_by` |
| `uploaded_unverified` | Client confirmed upload; server did a cheap metadata-only existence/size check | `pending_upload` | `verifying`, `cancelled` | server (on client confirm callback) | automatic | n/a | no | `vault_object_ref`, `size_bytes` |
| `verifying` | A worker has claimed the verification job | `uploaded_unverified` (also re-entrant from itself on worker re-claim after lease expiry) | `verified`, `verification_failed` | worker | automatic | n/a (the claim itself is retried by the claim query) | no | corresponding `catalog_verification_jobs` row `status='claimed'` |
| `verified` | Worker confirmed `verified_sha256` matches, technical metadata captured | `verifying` | (none — terminal for upload purposes; review_status takes over from here) | worker | automatic | n/a | **yes** | `verified_sha256`, `technical_metadata`, `duration_seconds` |
| `verification_failed` | Worker exhausted retries or found a definitive problem (hash mismatch, unsupported format, invalid duration) | `verifying` | (none) | worker | automatic | no (max attempts exhausted) | **yes** | `catalog_review_flags` row created (reason `verification_failed`/`hash_mismatch`/`unsupported_format`/`duration_invalid`) |
| `cancelled` | Explicit human decision to abandon this attempt | `pending_upload`, `uploaded_unverified`, `verifying` | (none) | human (admin) | human | no | **yes** | `reason` in the corresponding audit event |

**Illegal transitions** (all of these must be rejected by application code, since the DB CHECK only constrains the value set, not the graph): `verified → *` (once verified, a re-verification is a new asset version, not a state change on the old one); `verification_failed → verifying` directly (must go through a fresh upload attempt / new idempotency key, not "resume" a definitively failed one); any transition into `pending_upload` from a later state (no going backwards).

## 3. Verification worker contract

**Model: separate `catalog_verification_jobs` table (Option B), 1:1 with `catalog_asset_versions`** — not claim columns on the catalog-facing table, so worker plumbing (leases, retries, error codes) doesn't overload the entity a human reviewer looks at. Full column list and the exact claim/completion SQL pattern are in A1's own file comment — summarized here:

```
CLAIM:      atomic UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED
            ORDER BY next_attempt_at NULLS FIRST, created_at LIMIT 1)
            RETURNING *;
LEASE:      5 minutes (product assumption, not a guarantee — long enough
            for a stream-hash of a ≤250MB file at reasonable throughput).
RETRY:      exponential backoff (30s, 2m, 10m, ...), attempt_count
            incremented AT CLAIM time (not just on failure) so a
            crash-and-abandon still counts toward the cap.
MAX ATTEMPTS: 5 (product assumption). Past this, status='failed',
            upload_status flips to 'verification_failed', a review flag is
            created.
IDEMPOTENT COMPLETION: UPDATE ... WHERE status='claimed' AND
            claimed_by=$worker_id — a stale/lease-lost worker's completion
            attempt affects 0 rows and MUST NOT be treated as success by
            the caller.
STUCK RECOVERY: self-healing — a lease-expired row is already included in
            the claim query's WHERE clause, so the next poll re-claims it
            automatically. No separate cleanup job needed for this case.
TERMINAL FAILURE: status='failed' after max attempts — requires human
            review via catalog_review_flags.
AUDIT EVENTS: verification_claimed, hash_verified, verification_passed,
            verification_failed (see SUMG_REVIEW_AUDIT_AND_DELETION.md for
            the full taxonomy).
```

**Race conditions, proven:**

| Scenario | Outcome |
|---|---|
| Two workers race for the same job | `FOR UPDATE SKIP LOCKED` — the losing worker's subquery simply skips the row already locked by the winner; no double-claim possible, by Postgres's own row-locking semantics |
| Worker crashes after claim, before any work | Lease expires, row becomes re-claimable, `attempt_count` was already incremented at claim time so the crash counts toward the cap |
| Worker hashes the object, then dies before the DB update | Wasted compute, but no partial/corrupt state written — nothing is written until the final UPDATE. On lease expiry, a new worker redoes the hash. Wasteful, never unsafe |
| Lease expires while the original worker is still alive and about to complete | The `claimed_by` guard means the stale worker's completion UPDATE affects 0 rows — it must check the row count and log a "lost lease" warning, never assume success. The new claimant's result is what actually lands |
| Same job completes twice (duplicate trigger/message) | Second completion call matches 0 rows (`status` is no longer `'claimed'`) — safely inert |
| Permanently invalid file | After max attempts, terminal `failed`/`verification_failed`, review flag created, no infinite retry loop |

## 4. SHA-256 / duplicate contract

**client_sha256 vs. verified_sha256, never a single mutable field.** `client_sha256` is submitted by the browser before verification and is never trusted alone. `verified_sha256` is set only by the worker after re-hashing the stored object and is the only column any duplicate-detection or content-identity decision may use.

**Why re-verification can't be "cheap and synchronous":** checked directly against the one real object in production storage — its ETag (`"dd4a8709abe22ee3ec56b94cfa6239a9-1"`, confirmed via `storage.objects.metadata`) carries the standard S3 multipart-upload signature (MD5-of-part-MD5s + part count), which is **not** a usable content hash, and never SHA-256 regardless. The only way to get a real SHA-256 of what's actually in Storage is to read the bytes back and hash them — there is no shortcut, no trustworthy provider-supplied checksum to lean on instead. That read happens in the verification worker (a long-running process with no request-bound timeout/memory ceiling), streamed, never in a synchronous server-action response path.

**Duplicate detection, concurrency-safe:**

- Both `client_sha256` and `verified_sha256` are indexed (not unique — a hard uniqueness constraint would make the admin's deliberate "upload anyway as a new version" choice impossible).
- `client_sha256` powers an early, non-authoritative "might already exist" hint the UI can show before verification completes.
- The authoritative duplicate check runs against `verified_sha256` and only fires once a version's hash is actually confirmed.
- **Two identical files uploaded simultaneously, before either verifies:** both rows exist independently (`client_sha256` matching, `verified_sha256` both `NULL`); the UI can show the early advisory hint for both; the authoritative duplicate flag only fires once both have `verified_sha256` populated — at that point a `duplicate_detected` audit event fires and a `catalog_review_flags` row (`reason_code='duplicate_hash'`) is created for admin decision. **Neither copy is auto-merged, auto-deleted, or silently reused** — the admin explicitly chooses link-to-existing / keep-as-new-version / cancel.
